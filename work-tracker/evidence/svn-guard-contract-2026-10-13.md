## Conclusion

SVN can apply the existing **author-only** identity contract where the consumer's adopted committed policy names bare server account identities. It cannot satisfy a configured signature requirement. A pending SVN edit has no authenticated author, so it cannot count as an authorized protected change before commit. Harmless local reads need neither attribution nor a server.

The principal missing interface is a **trusted committed policy baseline for the consumer**, not a signature helper. Current SVN helpers establish revisions and line authors; none establishes an SVN equivalent of Git's trusted default-branch policy. A policy read from the candidate working copy or candidate revision cannot authorize that candidate to grant itself rights, remove `signed`, move the protected sections or declare a new baseline.

A bounded implementation can refuse unresolved protected changes and preserve existing local/shared operations. Adopting a new policy anchor, treating an arbitrary branch's own policy as the canonical policy, accepting unsigned migration from a signature-required policy, or crediting a pending SVN author are authority choices that must not be inferred from this brief.

## Proposed bounded change/proof contract

The following is a concrete contract proposal for Builder/Planner review. It does not supply the missing adoption authorization.

1. **Consumer identity and stable snapshot.** Obtain SVN working-copy repository UUID, repository URL/relative path and relevant BASE revisions from the consumer ROOT. Use explicit numeric operative and peg revisions for server reads; pin one server HEAD at the start of a normal history/gate run. Source HERE's Git checkout/archive provenance is unrelated and cannot provide consumer authority. Reject switched/foreign-repository protected paths or inconsistent snapshots when their relationship to the adopted consumer baseline cannot be established. No conventional `/trunk` path is inferred.
2. **Trusted baseline versus changes.** Treat an established adopted policy revision as the authority boundary, like the accepted base excluded from Git's branch judgement. Read its policy from the server at the exact revision/path. Working-copy BASE identifiers identify a comparison point; local policy bytes and a label claiming a baseline are not authorization. `svn_shipped_moves()` provides useful pending-versus-newest-revision mechanics, but its choice of HEAD is not proof that HEAD's policy is trusted (`6341–6374`).
3. **Committed ordinary changes.** Read candidate and predecessor views under each revision's own policy/path/headings for what changed. Judge the actor against the trusted baseline policy (or a successor policy accepted through that baseline), not the candidate's newly granted rights. At every policy transition, evaluate authority under the previous accepted policy first; only then can the new policy become an accepted successor. Changes earlier than the established adoption boundary are not automatically re-judged under today's spelling/rights.
4. **Pending changes.** Use local status/schedule/copy metadata and compare actual pending bytes/properties against their server-committed BASE views. A new protected text, policy alteration, protected deletion or unavailable baseline has no authenticated committer yet: refuse guarded acceptance before any derived write. `--username`, local credentials, `answered-by`, process user and prior blame are not the pending author. Allow untouched protected sections, exact initial scaffold, open/new trackers with no protected state and changes confined to unguarded Passes. Existing SVN rights still judge pending protected tracker lines under their current rules.
5. **Commit path limit.** Existing docs deliberately say command-line SVN commit has no client hook and attribution is judged after commit (`README.md:365–366`). Do not introduce a pre-commit exception that pretends to know the future author. A refusal in the tool is not a claim that the server itself prevents the commit. Supporting a stronger server-side admission scheme or a special pending-Owner bypass is new scope.
6. **Policy edits and redirects.** Enumerate changes to configuration as well as the old/new protected home and dependencies. A candidate cannot self-add its author, weaken proof, remove seats, redirect `tracker_dir`, rename headings, turn its guard off or hide a protected deletion. Byte-identical effective section moves retain their existing non-change meaning; any actual policy-authority change is still judged through the prior accepted policy. Preserve signers-file protection where such files are retained; do not attempt SVN signature verification.
7. **Copies.** Reuse `svn_blame`, first-path log and through-copy metadata: the protected content's original author and the copier must both hold the right under the applicable accepted policy. `svn_new` marks pending add/replace/copy as unauthenticated until commit. Whole existing content copied with no protected change is not a new Owner statement; when a copy creates a new protected state, its original attribution cannot be laundered through an authorized copier. Track copy-from URL/revision explicitly; do not read absent copy ancestry as fresh harmless text.
8. **Merges and restores.** Preserve current SVN rules: `blame -g` attributes a changed line in an existing path to its source author; a newly introduced path whose older lines arrive through a merge has `MERGED_IN` and refuses (`svn_blame:5207–5212,5233–5249`; `line_author:5369–5385`). A merger's allowed account cannot authorize an unauthorized source change. For section-level comparison, a verified pure carry must be traced to already accepted source text/changes; new synthesized text belongs to its actual recorded author. If source/reverse/nested/copy ancestry is incomplete, refuse the affected protected change rather than inventing Git parents or a blanket merger exception. Existing generic `section_changes` must not be passed guessed parent views.
9. **Missing proof.** Normal gate/history may contact the server. Missing command/login, unreadable repository/history, absent or empty author, malformed XML/revision/path, unresolvable ancestor/copy or signed-required mode gives a bounded refusal naming the affected file/revision and unavailable proof. `svn_run` returns `None` for legitimate absent-revision/path answers; a context requiring policy/author must reject that `None`, not turn it into empty permitted history. Failure must precede INDEX/board/worksheet writes in an ordinary write run.
10. **Local board and harmless reads.** `--html-only` and local read-only rendering start no server command and make no policy-verification attempt. Keep the interpreter tripwire and current SVN `provenance=False` path (`render_html` at `4471`; `board_run:9741–9787`). Display available local data with one truthful SVN proof-limit line, not an authenticated-author/guard-verified badge. Missing remote proof cannot block these reads. This does not weaken a gate: rendering and protected acceptance are different operations.

“Server-authenticated” remains the existing trust assumption about the consumer's SVN service and its author record. A nonempty `svn:author` string alone does not establish how that service authenticated its writer; local `file://` tests with a supplied username are not evidence of authenticated deployment. Do not claim new server-authentication verification from a successful read or silently accept anonymous/missing author attribution. A demand to verify arbitrary server configuration, administrative revision-property immutability or a new identity-proof mechanism would need its own scope; it is not implemented by this guard slice.

## Independent controls, prepared from the contracts

Research ran none. These are positive/refusal expectations, not copies of a Builder's new method names. No proof platform is selected under D4.

- **Bare account / rights positive:** committed protected edit by the baseline's bare Owner account passes author-only; non-Owner custom seat with accepted `answer` right also passes; exact legacy `[seats] owner`, top Owner and no-seats `answerers` fixtures retain their declared meanings.
- **Wrong or absent author:** identical protected edit by Builder/outside account, empty/missing author, anonymous/unproven attribution or login/history failure refuses. Changing only the local policy to name that actor must not flip the result.
- **Signatures:** signed top Owner, signed seat, mixed signed/unsigned effective seat list, signed legacy answerers-only and signed-old/unsigned-new migration all refuse unavailable proof. A control deleting only the `signed` suffix in pending/candidate policy must still fail.
- **Baseline safety:** candidate self-grant/remove policy, redirected tracker, malformed committed config and stale/mixed/switch/foreign-repository protected path refuse when the accepted predecessor or authority boundary cannot be established. Revert-after-unauthorized-change cannot erase the intervening rejected change from the checked interval.
- **Pending versus committed:** same protected bytes refuse pending (even with `--username`/matching `answered-by`) and pass only after a genuinely authenticated allowed commit. Pending Passes-only change, ordinary open tracker and exact known scaffold pass without new author authority.
- **Section semantics:** whitespace edit, section/heading deletion and semantic redirect are protected; whole tracker+configuration move retaining exact protected text is no section change. Policy authority changes remain separately checked. English and configured historical/localized headings preserve the existing first-heading rules.
- **Copy/merge laundering:** authorized copier cannot cleanse unauthorized source text; unauthorized copier cannot inherit authorized source authority; both-authorized ordinary copy passes where current rights allow. Introduced merge path/unknown ancestry refuses; existing-path genuine authorized source edit and resolved pure carry retain their supported meaning. Nested/reverse merge and restored-copy controls exercise the existing cases, not imagined two-parent SVN commits.
- **Server error distinctions:** denied/missing policy, empty log versus absent legitimate revision, malformed XML, missing copy source and interrupted server each refuse where proof is required; they do not become “no protected change”.
- **Board/local read separation:** with server unavailable and a process monitor rejecting every server-capable SVN/Git launch, local board/read-only rendering still works and claims no verification. Mutating SVN, network, producer/import and administrative/symlink/alias writes stay rejected by the tripwire/write rules.
- **Source/consumer separation:** an allowed Owner in source HERE, or a verified archive manifest, grants no rights in consumer ROOT. A Git source and SVN consumer with different policy must use only the consumer's adopted SVN authority. Git R14/default-branch/signature/every-parent controls remain unchanged.

## Decisions that remain genuinely new, if needed

No new decision is needed to preserve bare-account author-only semantics, reject unavailable configured signatures, reject missing attribution, refuse pending protected changes or retain local server-free rendering. Those follow the current signed path, accepted filing and existing identity/rights contracts.

The supplied records do **not** identify an SVN canonical policy/adoption revision or authorize trust in a branch's own newly written policy. If a consumer lacks an established adopted committed authority boundary, the safe bounded result is “cannot establish policy/author; protected change refused”, while ordinary unguarded local operations continue. If the product must accept that consumer's protected changes now, the exact Owner decision needed is: **which consumer repository UUID/path and committed revision is the adopted authority baseline, and what existing policy establishes it?** Do not substitute this source repository's Owner or invent a `/trunk` convention. Selecting a bootstrap migration that treats initial candidate authority as trusted, weakening a signed policy to author-only, or granting a pending author exception would be additional new decisions; none is proposed here.

There is also a bounded compatibility question if the brief demands changing the authority policy of all historical SVN revisions rather than judging changes after an adopted baseline. R26 holds legacy interpretation; the guard must report that boundary and refuse unresolved cases, not retroactively reinterpret every old revision. A policy/history migration beyond that needs a signed decision and separate scope.
